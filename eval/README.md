# Hungry Hippa Memory Challenge

A reproducible harness that asks one question: **what does an agent actually
retain, and what does it get wrong, with a memory runtime versus without one?**

Ten scenarios, two arms, one throwaway database per scenario. No network, no
LLM, no hand-written numbers.

```bash
python eval/harness.py            # rewrites eval/results.json and eval/REPORT.md
python eval/harness.py --stdout   # also print a summary
```

Runtime: about two seconds on a laptop, including the growth scenario
(2 000 episodes).

## Files

| File | What it is |
|---|---|
| `harness.py` | The harness. Deterministic; writes both output files from the run. |
| `check_results.py` | Re-runs the harness into a temp dir and compares the machine-independent metrics against `results.json`. Exits non-zero if they drift. Used by CI. |
| `fixtures.json` | Generic seed data. Contains **no personal information**: the actor is `Operator`, the projects are `Project A`/`Project B`, components are `fixture jig`, `component B`, `Vendor A`. Fixture text is invented. |
| `results.json` | Machine-readable results of an actual run (regenerated by the harness). |
| `REPORT.md` | Human-readable report, generated from `results.json` so it cannot drift from the numbers. |

## The two arms

| Arm | What it has |
|---|---|
| `without` — **session-transcript-only agent** | Everything said in the current session, unranked and unbounded. No store, no budget, no access policy, no supersession state. When the session ends, it is gone. |
| `with` — **Hungry Hippa** | The real runtime from this repository, on a temp database: `build_context()` over episodic + semantic + graph memory, with the context compiler, the actor policy and quarantine. |

Both arms are read by the **same deterministic reader**: given the assembled
context and a question, it looks for the expected token and for any forbidden
token. So the only variable is the context source, not the "agent".

Vectors are disabled in the harness. Enabling local Ollama embeddings would make
results depend on a model version and on a running server; the harness stays
offline and repeatable instead, and says so rather than quietly mixing modes.

## Scenarios

| # | Scenario | What it measures |
|---|---|---|
| 1 | Cross-session factual recall | Reopening the store in a new session |
| 2 | Decision and rationale recall | Whether the *reason* comes back, not just the choice |
| 3 | Avoiding a previously failed solution | Would the agent repeat the failure? |
| 4 | Resolving superseded information | Current claim wins; the stale one does not resurface |
| 5 | Retrieval within a fixed budget | Context supplied under an explicit character budget |
| 6 | Cross-agent memory portability | A second client process on the same store |
| 7 | User-directed forgetting | Recall before, gone after, row still recoverable |
| 8 | Resistance to poisoned memory | An untrusted writer's claim never reaches the owner |
| 9 | Unauthorized retrieval attempt | Denial for untrusted, access for the owner |
| 10 | Performance as storage grows | Retrieval latency, storage size, context size at 100/500/2000 episodes |

## Grading, honestly

- Grading is **exact token matching** on the assembled context. It is coarse.
  It cannot tell whether an answer is well phrased or subtly wrong in a way that
  does not involve the expected/forbidden tokens. Anything needing judgement is
  listed under `unsupported` in `results.json` and in the report.
- A baseline arm that is **not comparable** is marked `unsupported`, never
  scored as zero:
  - scenario 8: the baseline has no store, so it cannot be poisoned;
  - scenario 9: the baseline has no access control, so denial accuracy is
    undefined.
- Aggregate rates are computed over the **comparable set only** (both arms
  gradable on the same question). The report prints which scenarios are in that
  set.
- "Incorrect memory" means a forbidden token (the stale or poisoned claim) is
  present in the context, which is the failure mode that matters for a memory
  system: confidently repeating something untrue.
- Latency numbers are wall-clock medians on the machine that ran the harness.
  They are not a benchmark and are not comparable across machines; the useful
  signal is the *shape* across growth points, not the absolute milliseconds.

## What this harness does not test

- Anything requiring an LLM judge (answer quality, semantic equivalence).
- Vector/embedding recall quality (disabled on purpose).
- Concurrency or multi-process write contention.
- Multi-user or cross-tenant isolation (not implemented in the runtime).
- Adversarial security testing beyond the policy checks in scenarios 8 and 9 —
  that lives in `tests/test_security.py`.

## Adding a scenario

1. Add any fixture text to `fixtures.json` (keep it personal-data-free).
2. Write a `scenario_N_*()` function that returns `{id, name, question, with,
   without, metrics, notes}`; give each arm a `correct` and `incorrect_memory`
   key when the arm is gradable.
3. Append it to `SCENARIOS`.
4. Re-run the harness and commit the regenerated `results.json` and `REPORT.md`.

Do not hand-edit `results.json` or `REPORT.md`; they are outputs. If a number
looks wrong, fix the harness and re-run.

## HH-08 ingest e2e (ChatGPT export → recall)

A separate path from the ten-scenario harness. It is the first *imported-history*
check: synthetic ChatGPT export → persist → optional local extract → recall/why.

```bash
python eval/ingest_e2e.py --offline --json    # CI: no chat model
python eval/ingest_e2e.py                     # live extract if LM Studio is up
python tests/test_ingest_e2e.py               # wired into scripts/check_all.py
```

- Fixture: `eval/fixtures/chatgpt_e2e_conversations.json` — invented workshop
  mill notes with a planted dated fact (`52Nm` on 12 March 2026). **Not** a real
  ChatGPT export; do not replace it with the operator's `conversations.json`.
- Database: throwaway `HUNGRY_HIPPA_DB` under `/tmp`. Live Hermes/Grok stores
  are refused.
- Live extract is optional. When LM Studio chat is down the suite still passes
  by proving ingest persist + recall of a directly stored owner memory whose
  evidence points at the planted ingest turn.
- Extracted hypotheses remain quarantined. The live demo uses owner CLI
  `recall --quarantined`; default recall must hide them.
- The report records retrieval `latency_ms` and whether the answer was
  supported by evidence ids. MCP remains six tools.
